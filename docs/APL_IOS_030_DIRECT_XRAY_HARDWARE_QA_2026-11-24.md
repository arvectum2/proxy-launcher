# iOS 0.3.0 — independent direct-Xray iPhone diagnostic, 24 Nov 2026

Goal: separate the real iPhone VLESS/REALITY failure in the pinned iOS `libXray` host runtime from a `NetworkExtension` / TUN / underlay-binding failure. The previous signed r15 direct-SOCKS and r19 Safari probes lacked an independent HTTP receipt; a Mac Xray CLI using the same synthetic REALITY peer does receive the exact HTTP receipt. No cause established yet.

Created `mobile/ios/Tools/DirectVLESSHardwareQA`: an isolated SwiftUI host diagnostic running pinned source-built `libXray` in the **host process**, with no NetworkExtension, App Group, Keychain, user-profile access, background VPN or production integration. Explicit `--apl-vless-direct-qa` plus a single consumed input file is mandatory; endpoint is fixed to the synthetic LAN peer `192.168.1.80:39882`, SNI `example.com`, local SOCKS `127.0.0.1:39879` and fixed RFC5737 target `198.51.100.77:39883`, with 40-character ASCII hex nonce. It reports only a run ID, coarse SOCKS greeting/CONNECT stage, exact nonce HTTP receipt and post-run Xray stop verification. Input containing the synthetic link is removed before native execution. No user Keychain contents are read.

The build script verifies the pinned source-built iOS libXray library/header SHA256 using the existing repository source pin, compiles a standalone unsigned ARM64 iPhoneOS app, checks native CGoInvoke linkage and bundle identity, and emits only a manifest. It does not sign, install or start the app. It does not alter the production iOS app or its advertisements. Dedicated safety source gates are checked by 4 new Python tests, including explicit trigger, strict synthetic endpoints and absence of VPN/Keychain/CloudKit API usage.

## Supervised unlocked iPhone 13, 24 November 2026 — exact device observations

**Interpretation:** physical VLESS egress remains **NOT ACCEPTED**. This test does NOT isolate an inherent `libXray` bug: an ordinary host-app TCP socket could not reach the exact private LAN peer either. Plausible unresolved causes include iPhone not sharing the Mac mini's Wi-Fi/LAN, OS Local Network permission not granted to the disposable QA app, or routing through the user's existing active VPN. This result must not be reported as proof of any one cause. Before any further VLESS-engine diagnosis, verify device LAN and iOS Local Network authorization; if routing interference needs isolation, obtain separate explicit authorization before changing an owner VPN. Do not repeat synthetic tests without a changed network precondition. Keep VLESS disabled in the release.
