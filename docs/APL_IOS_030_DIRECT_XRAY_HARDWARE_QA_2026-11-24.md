# iOS 0.3.0 — independent direct-Xray iPhone diagnostic, 24 Nov 2026

Goal: separate the real iPhone VLESS/REALITY failure in the pinned iOS `libXray` host runtime from a `NetworkExtension` / TUN / underlay-binding failure. The previous signed r15 direct-SOCKS and r19 Safari probes lacked an independent HTTP receipt; a Mac Xray CLI using the same synthetic REALITY peer does receive the exact HTTP receipt. No cause established yet.

Created `mobile/ios/Tools/DirectVLESSHardwareQA`: an isolated SwiftUI host diagnostic running pinned source-built `libXray` in the **host process**, with no NetworkExtension, App Group, Keychain, user-profile access, background VPN or production integration. Explicit `--apl-vless-direct-qa` plus a single consumed input file is mandatory; endpoint is fixed to the synthetic LAN peer `192.168.1.80:39882`, SNI `example.com`, local SOCKS `127.0.0.1:39879` and fixed RFC5737 target `198.51.100.77:39883`, with 40-character ASCII hex nonce. It reports only a run ID, coarse SOCKS greeting/CONNECT stage, exact nonce HTTP receipt and post-run Xray stop verification. Input containing the synthetic link is removed before native execution. No user Keychain contents are read.

The build script verifies the pinned source-built iOS libXray library/header SHA256 using the existing repository source pin, compiles a standalone unsigned ARM64 iPhoneOS app, checks native CGoInvoke linkage and bundle identity, and emits only a manifest. It does not sign, install or start the app. It does not alter the production iOS app or its advertisements. Dedicated safety source gates are checked by 4 new Python tests, including explicit trigger, strict synthetic endpoints and absence of VPN/Keychain/CloudKit API usage.

## Independent iOS Local Network privacy blocker confirmed (same Wi-Fi, 24 Nov)

After the owner confirmed the iPhone and Mac mini are on the **same Wi-Fi**, tested a QA-only direct TCP socket without libXray, user profiles, PacketTunnel or VPN changes. The macOS firewall is off, block-all disabled, and a local Mac client successfully connects to the listener on `192.168.1.80:39882`.

- Signed isolated `DirectXrayQA` iPhone run `native-artifacts/ios-030-lan-socket-gate-20261124/iphone-result.json`: `wifiHasIPv4=true`, `wifiOnTestSubnet=true` (the iPhone's `en0` address is in `192.168.1.0/24`, **no actual client IP persisted**), `directLANReachable=false`, `lanErrorCode=65` (`EHOSTUNREACH`), `lanPhase=connect`, `xrayWasNotStarted=true`. The independent Mac bound listener received one positive-control Mac accept and **zero non-self accepts**.
- Upgraded same isolated app diagnostic to use `Network.NWConnection` for an additional bounded 3-second endpoint-specific privacy path probe. After preflighting the QA binary and explicitly terminating **only the pre-existing QA app process** (a second `devicectl launch` without terminate reuses the existing process and does NOT rerun SwiftUI task arguments), a fresh one-shot physical report `native-artifacts/ios-030-nwprivacy-fresh-process-20261124/iphone-nwpath-result.json` confirmed `nwConnectionState="waiting"` and `nwLocalNetworkDenied=true`, alongside the same iPhone IPv4 subnet and `EHOSTUNREACH(65)`; `xrayWasNotStarted=true`.
- This is definitive evidence that the disposable **QA app's own Local Network privilege is denied/blocked** in its current iOS session, not proof of a REALITY handshake or `libXray` defect. Do not infer that the **production** APL app has the same permission state; it is a distinct bundle. It also does not prove the owner's existing VPN route is healthy. No production code/runtime, Apple capability, VPN, user profile or advertising changed.
- Apple primary reference: https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy.md — outgoing LAN TCP requires per-app Local Network authorization; `NWConnection.State.waiting` with `NWPath.UnsatisfiedReason.localNetworkDenied` is the supported diagnosis. Such a connection can initially be denied before the user responds to the consent alert. The correct next action is a **user-controlled** switch under iPhone `Settings > Privacy & Security > Local Network > APL Direct Xray QA`, not an unauthorized VPN switch or Apple Developer capability update.
- QA host-only runtime is now **fail-closed**: if bounded LAN check fails, it records `localNetworkPermissionDenied` or `lanUnavailable` and **does not start Xray**. No false SOCKS CONNECT acceptance or repeated failed peer handshakes. Seven dedicated QA source tests plus the previous four first-TLS-record tests passed; current iOS release Python50/preflight passed.
- Signed final off-device QA candidate at private `native-artifacts/ios-030-direct-xray-qa-signed-local-network-gate-20261124/DirectXrayQA.app` is built and code-signed with existing wildcard development credentials, *not* a product or App Store build.
