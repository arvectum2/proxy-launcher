# APL iOS 0.2.0 — автоматическое обнаружение зависимостей исключаемого сайта

**Дата:** 02.11.2026 · Задача `APL-SMART-DEPENDENCIES-AUTO-20261102` · PR #296 (Draft).

## Исходный продуктовый сценарий

**Пользователь добавляет сайт A → APL открывает его и наблюдает HTML/фактические запросы → выявляет ресурсы B/C → добавляет надёжные зависимости либо предлагает одобрить неоднозначные.** Никакого дополнительного Gateway/VPS, альтернативного VPN или покупки прокси для этого не требуется. Gateway-эксперимент `df0f11c3` отозван из ветки отдельным `git revert`: это была неверная интерпретация исходной задачи.

## Реализация

1. `ExclusionsView.addEntry()` теперь автоматически ставит любой новый нормализованный **домен** в очередь WebKit-сканирования; IP literal без сайта не сканируется. Если добавлено несколько адресов — очередь последовательна. **Save отключён**, пока идёт анализ, чтобы пользователь мог увидеть дополнительные решения до сохранения. Ручное повторное «Найти связанные домены», остановка анализа, удаление, «Очистить все», Undo и сохранение/откат продолжают работать.
2. `ExclusionWebScanner` в ephemeral WebKit открывает сайт в пределах apex/www, читает HTML и реальные `PerformanceResourceTiming` запросы, даёт дополнительную **1,2-секундную паузу** после загрузки для XHR/скриптов, ограничивает время и данные. Важно: WebKit не выполняет сценарии после логина/кликов, не гарантирует обнаружение всех отложенных зависимостей. Публичные сайты без доступной сети могут дать пустой/ошибочный scan, но вручную добавленный сайт сохраняется.
3. `SmartExclusionGraph.approveStrongFirstParty` автоматически утверждает **только явно наблюдавшиеся в HTML И фактических запросах** поддомены A, которые отвечают строгой проверке имени, не выглядят как tracker/ads/analytics/pixel и не были ранее отклонены пользователем. Каждое утверждение проверяет лимит 32 эффективных исключений; если превышен — остаётся pending. При повторном сканировании уже сделанные пользователем approved/rejected решения не перезаписываются, граф истекает по прежнему TTL 7 дней.
4. Слабо подтверждённые поддомены (видны только в HTML либо только в запросах) остаются **кандидатами для нажатия «Подтвердить выбранные для обхода»**. Сторонние домены B/C из `<script>`, `<link>`, `<img>`, `<iframe>`, `<form>` или реальных запросов показываются отдельно — **только с индивидуальным подтверждением**, потому что это могут быть реклама, аналитика и общие CDN. Переходы по обычным `<a href>` не считаются зависимостями.
5. UI показывает раздел «Добавлены автоматически»: сюда входят одобренные связи, www/apex-алиасы и ранее проверенные совместимые ресурсы (например, `gosuslugi.ru` → `gu-st.ru`). Уже включённые домены не предлагаются второй раз. Удаление главного A снимает связанные правила; сохранение применяет изменения через существующий `AppViewModel.saveExclusions` с атомарным rollback при проблеме VPN.

## Ограничение, не смешивать с автообнаружением

Данная задача **находит зависимости**. Она не устраняет фундаментальную особенность локального `NEIPv4/6.excludedRoutes`: IP-исключение способно охватить другие домены на том же CDN IP. Ранее добавленный `SharedIPRouteGuard` блокирует обнаруженные коллизии, но для неизвестных доменов абсолютной изоляции нет. Это отдельная будущая архитектурная задача, а не условие обнаружения B/C. Не заявлять «гарантированно найдены все ресурсы» или «гарантированно только эти домены идут мимо VPN».
