# APL macOS 0.2.21 — App Store VPN migration regression, 2026-11-04

## Root cause (physical MacBook Air)

Installed Mac App Store 0.2.21 build 15 immediately failed to connect to VPN.
The macOS NetworkExtension validation log repeatedly showed:
- nesessionmanager: Signature check failed (code requirement not satisfied)
- NEVPNTunnelPlugin: Validation of the extension failed
- NEVPNConnectionErrorDomainPlugin code 7

The app and Packet Tunnel both passed independent codesign strict verification,
signed with Apple Mac OS Application Signing and team VML75VY94V. The
persisted system VPN manager retained a signer requirement from the earlier
TestFlight/developer-signed installation. The existing reconcile() compared
only marketing version 0.2.21, which can be unchanged across distribution
channels and build numbers; reusing the manager was insufficient.

## Safe confirmed restoration

- Backed up the App Group profile preferences on MacBook to
  ~/Library/Application Support/ArvectumQA/20261104/recovery/.
- All three profiles were intact: Нидерланды 2, Основной, Резерв США.
  The PX6 primary 68.209.60.141:8000 still times out; the US backup
  200.0.60.91:9448 is reachable. Selected Резерв США without altering
  any passwords.
- Deleted ONLY the stopped Arvectum Proxy Launcher VPN configuration in
  macOS System Settings. Native Tailscale VPN configuration was preserved.
- Reconnected via the installed signed App Store build 15 and approved the
  fresh macOS VPN authorization prompt. New service ID:
  C985B8FB-3348-4FC3-8A59-E5B1D41C8677.
- Physical result: VPN Connected, 15/15 parallel HTTPS 200, external
  proxy egress 200.0.60.91. At the 17-minute recheck: TCP 23, CLOSE_WAIT 0,
  VPN still Connected, ARC userspace Tailscale Running/Online. Three proxy
  profiles and credentials preserved. App Store app was NOT replaced.

## Future source-level prevention

- macOS AppShared now exposes CFBundleVersion (build).
- VPNController refreshes the saved manager when either marketing version OR
  build number changes.
- macOS Settings adds a confirmation-protected Восстановить VPN control.
  The explicit action removes only stopped VPN managers belonging to this
  application, creates a new NETunnelProviderManager and requests standard
  macOS authorization. It never touches App Group profiles or Keychain,
  never acts silently on app launch and never removes Tailscale.
- Tests: macOS App Store contract 23/23 PASS, appearance 5/5 PASS;
  standalone macCatalyst swiftc typecheck of changed VPNController PASS.
- Full source tree Mac Catalyst build from latest origin/main remains blocked
  by an unrelated native dependency mismatch: new SmartFlowEventCollector
  expects tun2proxy_set_flow_event_callback and
  tun2proxy_set_direct_exact_host, absent in available macOS Catalyst
  tun2proxy.xcframework. This is not a failure of the VPN controller typecheck.
  No rebuilt/signed replacement app was installed or submitted here.

## Separate socket pressure issue

Earlier App Group telemetry recorded up to 1689 upstream TCP sockets, of
which roughly 1655 were CLOSE_WAIT, with repeated connection-pressure events.
This remains a separate potential tun2proxy lifecycle leak. The actual
App Store update connection failure was caused by stale VPN signature
validation, before any upstream proxy call. Short stable US backup tests
do NOT establish that the historical socket leak is permanently fixed.
Investigate under controlled physical QA without exceeding upstream
providers' caps; do not conflate the two incidents.
