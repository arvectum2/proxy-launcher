# APL macOS 0.2.20 candidate — bounded upstream connections

Status: **macOS 0.2.20 build 9 accepted by Apple, TestFlight Internal QA in progress; NOT PUBLICLY RELEASED** (2026-10-30).

## Problem observed

On a MacBook running APL macOS 0.2.19, the Packet Tunnel process held
333–336 TCP connections to a single upstream proxy, including 179–185 in
CLOSE_WAIT. Restarting the tunnel immediately reduced this to 8 connections.
During subsequent usage the socket count started rising again. A provider
reported a 200-connection cap on a different proxy; its server-side accounting
has **not** been independently verified.

## Changes in this candidate

- Packet Tunnel periodically counts *its own* connected TCP sockets to the
  selected upstream host and port using public Darwin APIs. Inspects Darwin
  TCP state, including CLOSE_WAIT, without reading credentials or using shell.
- After two consecutive 30-second measurements with >=90 upstream sockets
  or >=35 CLOSE_WAIT sockets, recycle only the embedded tun2proxy engine.
  Emergency threshold: >=150 sockets or >=85 CLOSE_WAIT immediately.
- Never recycle more than once per 15 minutes. No action during switching
  or stopping. Works for manually selected and Auto-mode profiles alike.
- TLSProxyRelay releases both closed NWConnection instances immediately,
  rather than retaining all connections until complete VPN shutdown.
- Recorded telemetry has only profile name and aggregate socket counters;
  never a password or authentication header.
- Retain existing profile selection, PAC, Tailscale and external ARC behavior.

The policy is a **safety net**, not a proof that the root cause in tun2proxy
v0.8.3 has been eliminated; upstream lifecycle analysis remains required.
