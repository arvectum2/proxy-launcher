# APL macOS 0.2.20 candidate — bounded upstream connections

Status: **engineering candidate / NOT RELEASED** (2026-10-30).

## Problem observed

On a MacBook running APL macOS 0.2.19, the Packet Tunnel process held
333–336 TCP connections to a single upstream proxy, including 179–185 in
CLOSE_WAIT. Restarting the tunnel immediately reduced this to 8 connections.
During subsequent usage the socket count started rising again. A provider
reported a 200-connection cap on a different proxy; its server-side accounting
has **not** been independently verified.

## Changes in this candidate

- Packet Tunnel periodically counts *its own* connected TCP sockets to the
  selected upstream host and port using public Darwin APIs. Inspects Darwin
  TCP state, including CLOSE_WAIT, without reading credentials or using shell.
- After two consecutive 30-second measurements with >=90 upstream sockets
  or >=35 CLOSE_WAIT sockets, recycle only the embedded tun2proxy engine.
  Emergency threshold: >=150 sockets or >=85 CLOSE_WAIT immediately.
- Never recycle more than once per 15 minutes. No action during switching
  or stopping. Works for manually selected and Auto-mode profiles alike.
- TLSProxyRelay releases both closed NWConnection instances immediately,
  rather than retaining all connections until complete VPN shutdown.
- Recorded telemetry has only profile name and aggregate socket counters;
  never a password or authentication header.
- Retain existing profile selection, PAC, Tailscale and external ARC behavior.

The policy is a **safety net**, not a proof that the root cause in tun2proxy
v0.8.3 has been eliminated; upstream lifecycle analysis remains required.

## Acceptance gates before publication

1. Unit-test normal usage, sustained resource pressure, emergency threshold,
   switch-in-progress, recovery cooldown and subsequent recovery.
2. Build PacketTunnelMac with the pinned tun2proxy Catalyst framework.
3. Complete full Mac Catalyst app build from current main. On 2026-10-30,
   that build was blocked by existing macOS target exclusions for
   AppearanceMode / AppLanguage; separate fix is needed.
4. Rebuild the exact pinned patched tun2proxy library for release; the
   cached library used for compile verification does not contain the current
   exact-host split-DNS patch and is **NOT** a release artifact.
5. Install an appropriately signed test build on a physical MacBook and run
   60+ minutes of realistic multi-tab usage, including HTTPS CONNECT and
   DNS/exclusions; compare upstream sockets and CLOSE_WAIT before/after.
6. Verify manual and Auto profiles, failover/return-to-primary, PAC-independent
   routing, Tailscale userspace for ARC and no unintended GUI Tailscale VPN.
7. Test on iOS separately **after** the ongoing 0.1.40 App Review. Do not
   modify or replace that current submission. iOS release version undecided.
8. Increment the macOS marketing/build numbers only after acceptance.
   Never replace already published version assets in place.

Existing local MacBook LaunchAgent socket guard is a temporary mitigation.
Remove it only after accepting the new in-process protection on the actual
device; do not run two competing automatic recovery mechanisms indefinitely.
