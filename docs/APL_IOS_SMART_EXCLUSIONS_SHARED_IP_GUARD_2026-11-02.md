# Smart Exclusions 2.0 — shared-IP guard, DNS proof, exact-host routing gate

**Дата:** 02.11.2026 · iOS 0.2.0 (48), Draft PR #296 · задача `APL-SMART-EXCL-020`. **Статус: частичная защита в исходниках, полная приёмка точного обхода доменов ещё не достигнута.**

## 1. Подтверждённая проблема

`PacketTunnelProvider.resolveExclusions` формировал `/32` и `/128` системные `NEIPv4/NEIPv6.excludedRoutes` из DNS-ответов каждого разрешённого домена. Патч `tun2proxy --dns-bypass HOST=IP` обеспечивает DNS-ответ реальным IP для разрешённого домена и виртуальным IP для неизвестного (обычно работает), но **системная IP-маршрутизация глобальна для всех соединений с этим IP**. При общих IP/CDN *независимый* браузер, сторонний DoH/прямой IP или другое приложение может выйти DIRECT даже если его домен не был разрешён пользователем. Нельзя делать заявления «только эти домены обходят VPN» без проверки per-flow identity.

Официальное основание: https://developer.apple.com/documentation/networkextension/routing-your-vpn-network-traffic и https://developer.apple.com/documentation/networkextension/neipv4settings/excludedroutes .

## 2. Реализованная адресная доработка (без изменения Apple/пользовательского iPhone)

- `SharedCore/SharedIPRouteGuard.swift`: отслеживает адреса разрешённых доменов и *заведомо не разрешённых* (pending/rejected) детей активного `SmartExclusionGraph`. Если реальный IPv4/IPv6 совпадает, **не создаёт** прямой `excludedRoute` и `--dns-bypass` для конфликтующего имени, весь его набор адресов остаётся в обычном прокси. Невозможность разрешить имя из известного отрицательного списка — **fail-closed** для опциональных прямых доменов.
- IP-адреса **канонизируются численно**, включая разные записи IPv6 `2001:0db8::42` / `2001:db8::42`; не сравнивать сырой текст.
- `PacketTunnelProvider` подключён к новому guard перед формированием `excludedRoutes`. Список неразрешённых DNS-проверок ограничен 32 именами; при превышении лимита **не выполняем сотни DNS-проб, все необязательные прямые доменные маршруты блокируются**. Апстрим-прокси остаётся доступным (его транспортный IP исключён отдельно), а его пароль никогда не добавляется в telemetry.
- `SharedIPRouteGuardTests` 7/7 PASS: разные IP и реальные first-party связи, IPv4/IPv6 common CDN, IPv6 canonicalization, неопределённый DNS ответ, частичное совпадение, ручной IP literal и полный `SmartExclusionGraph` approve/reject. Полная Swift Core 113/113 PASS.
- `scripts/ios_smart_exclusions_shared_ip_lab.py`: настоящий HTTP/TCP server + настоящий локальный прокси на loopback, **разные Host на единственном реальном IP**. Показан старый ошибочный IP-wide egress: разрешённые `site.test`, `api.site.test`, `static.site.test` и запрещённый `tracker.site.test` попали бы DIRECT. Конфликт IP в новом guarded-плане приводит к **PROXY для всех четырёх** (fail-closed); при отсутствии конфликта связанные HTML/JS/CSS/API-сокеты проходят DIRECT. Это **сетевой лабораторный тест модели**, а не реальный iOS Network Extension E2E; не выдавать его за последний.
- Существующие 8/8 Python Smart Exclusions test contracts PASS; ARM64 iOS Simulator BUILD SUCCEEDED с `SharedIPRouteGuard` в app + extension. До релиза нужна отдельная физическая приёмка.

## 3. Объективный остаточный риск / блокер полной приёмки

Защита срабатывает **только для обнаруженных и сохранённых неразрешённых имён**. Graph обнаружения намеренно содержит лишь первые-party поддомены; произвольные независимые имена/DoH/мобильные приложения с IP literal вообще не попадают в этот список. Даже когда граф пуст, любой IP-wide `excludedRoute` способен выпустить такой трафик наружу. Следовательно, **гарантия, что посторонний сайт на shared CDN IP не выйдет DIRECT, сейчас отсутствует**. Экстренно удалять все `/32` для разрешённых доменов нельзя: это сломает пользовательские исключения, включая `gosuslugi.ru`/`gu-st.ru`. Сейчас действует ограниченное защитное дополнение, не обещанное как абсолютный фикс.

**Требуется `APL-SMART-FLOW-001`: перехват на уровне каждого нового потока в движке** (не пытаться применить списки IP). Рекомендуемая архитектура:

1. **Идентификация:** virtual DNS связывает точный, явно разрешённый QNAME с уникальным fake-IP с TTL; `tun2proxy` перед установлением TCP/UDP соединения должен проверить виртуальный IP → зарегистрированный разрешённый hostname. Никакого доверия к SNI/HTTP Host, если он противоречит DNS-идентификатору; DoH, raw-IP, ECH/неопределённый origin **PROXY**.
2. **Маршрут:** прямой outbound создаётся отдельно как *управляемый физически scoped socket вне TUN*, с разрешённым реальным IP и успешной независимой IPv4/IPv6 проверкой. Из iOS `NEPacketTunnelProvider` нельзя просто открыть неподконтрольный сокет: необходим эксперимент с Network Extension/Network.framework physical-interface binding, предотвращением recirculation и переключением Wi-Fi/LTE. При невозможности доказать маршрут — **PROXY**. Не создавать IP-wide `excludedRoutes` для сайтов; оставить только необходимый защищённый upstream transport, рассматривая его отдельные риски.
3. **Семантика:** ручное подтверждение связанных доменов; строгий default `PROXY`, нет суффиксных/глобальных wildcard-политик; TCP+UDP/QUIC, DNS A/AAAA/CNAME/TTL, shared CDN, IPv6, стирание отзыва и динамические обновления только после новой политики, без сброса пользовательских настроек.
4. **Физический E2E:** контролируемый один IP с двумя TLS-виртуальными хостами и независимым прокси; разрешённый сайт + CSS/JS/API выходит DIRECT, неразрешённый на том же IP — PROXY, IPv4 и IPv6, инвалидация DNS, VPN reset, Wi-Fi↔LTE, реальная IP/pcap-телеметрия обоих маршрутов и аварийный rollback на iPhone. Проверки должны доказать **одновременно оба разных egress**, а не только DNS или UI.

## 4. Релизное решение

`APL-SMART-EXCL-020` имеет **частичный implementation milestone** — guard детектированных коллизий. **Нельзя отмечать всю задачу completed**, пока нет работающего per-flow engine и физического shared-IP E2E. Настоящая ветка остаётся Draft, никакой новой IPA или App Review не выполнялось, старые профили/iPhone/Apple 0.1.41/РСЯ/privacy metadata не затронуты. Если per-flow не успевает в 0.2.0, релизное описание должно честно объяснять ограничения IP-wide исключений, а рискованные расширенные правила не включать без отдельного решения владельца.
