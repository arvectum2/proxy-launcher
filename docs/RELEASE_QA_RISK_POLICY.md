# APL — регламент релизных проверок по риску изменений

Статус: **принят** 04.11.2026. Применяется к macOS, Windows, Linux, iOS и Android с учётом платформенных требований.

## Цель и основной принцип

Проверяем **изменённое поведение и риски**, а не запускаем одинаковый тест на 65 минут после каждой сборки. Продолжительность сама по себе не является доказательством стабильности. Релизный QA должен быть воспроизводимым, достаточным по покрытию и не дублировать уже проверенные неизменные компоненты.

| Уровень | Что меняется | Минимальная адресная проверка |
| --- | --- | --- |
| R0 — контент | Тексты, локализации, визуальные элементы без логики соединений | Сборка, lint/контракты, краткий UI smoke (включая релевантные языки и устройства). Часовой сетевой тест **не нужен** |
| R1 — прикладная логика | Профили, настройки, импорт/экспорт, исключения без изменения сетевого движка | Адресные тесты и **5–10 минут** проверки сценариев на устройстве: сохранность данных, обновление, подключение и откат |
| R2 — сетевое поведение | Маршрутизация, VPN/TUN, переключение прокси, DNS, TCP/CONNECT, изменение общего сетевого кода | Unit/integration tests с контролируемыми ошибками и **10–15 минут** нагрузки на настоящем устройстве; проверить CONNECT, HTTPS, переключение, маршруты, PID и доступность ARC |
| R3 — управление сокетами / известная утечка | Жизненный цикл TCP, half-close, FIN, CLOSE_WAIT, тайм-ауты/лимиты, повторное накопление соединений | Native regression с настоящим TCP FIN + стресс + **60–65 минут** физической проверки подписанной сборки. После исправления накопления — обязательно, не заменять коротким тестом |

**Эскалация:** тестируем по наивысшему затронутому уровню. Новый номер сборки, переподписание либо изменение только UI **сами по себе** не требуют повторного часового теста. Если после длинной приёмки изменился сетевой движок или общая маршрутизация, уровень оценивается заново; при изменениях управления сокетами или риске повторной утечки — повторяем R3. При реальном сбое во время теста выясняем его причину, исправляем и повторяем необходимую приёмку. Не запускаем новый 65-минутный прогон автоматически без объяснения, какую гипотезу он проверяет.

## Функциональные критерии приёмки сетевых релизов

Пороговые значения TCP/CLOSE_WAIT берём из актуальной реализации и спецификации тестового стенда; нельзя произвольно менять лимиты ради «PASS».

- TCP-сессии и CLOSE_WAIT ограничены; после нагрузки закрытые соединения освобождаются и **нет устойчивого роста** за окна измерений.
- Запросы HTTPS и CONNECT проходят; проверяются основной прокси и резервный при наличии тестового отказа, а также возврат к основному согласно политике.
- VPN/TUN сохраняет рабочее состояние, без непредусмотренного переподключения и смены PID; пользовательские профили и секреты не утрачены.
- ARC/Tailscale контролируются **отдельно** от APL: внутренний статус и независимый внешний доступ не подменяют друг друга. Ошибки инфраструктуры фиксируются, но не объявляются автоматически дефектом прокси.
- Реальный тайм-аут HTTPS — **не PASS**. Его расследуют: проверяют несколько независимых адресов, доступность upstream-прокси и маршрут APL. Отсутствие роста CLOSE_WAIT не отменяет сбоя доступности.
- Сохраняем исходные измерения, версию/номер build, commit, устройство, длительность, метод проверки, результаты и отдельные оговорки. Результат автоматического анализатора нельзя переписывать вручную; экспертное заключение указывают отдельно.

## Релизный порядок

1. Определить риск по diff исходников, включая общий код/зависимости, а не по названию задачи или номеру версии.
2. Проверить lint, тесты, сборку, подпись и обновление с сохранением профилей. Не повторять незатронутые испытания без причины.
3. Пройти адресную физическую QA соответствующего уровня и зафиксировать артефакты.
4. При критическом дефекте или проваленном критерии — блокировать публикацию и устранить причину; при внешнем блокере — честно зафиксировать источник и отдельно решить достаточность доказательств.
5. Только после выполнения обязательных gate, успешного CI и проверки соответствия **исходный commit → подписанный binary → App Store build** объединять код и отправлять релиз. Не считать загрузку в TestFlight публичной публикацией.

## Применение к macOS 0.2.22

- Build 16 выявила длительную утечку CLOSE_WAIT — R3 был необходим.
- Build 17 прошла повторную 65-минутную проверку, но первая попытка выявила два тайм-аута HTTPS, поэтому повтор был обоснован.
- Для build 18 изменился также общий код маршрутизации, поэтому назначена отдельная физическая приёмка подписанного бинарника.
- **После завершения build 18 не назначать ещё один 65-минутный тест автоматически.** Следующий тест — только по конкретной причине и фактическому изменению риска.

Платформенные обязательные требования (например, конкретная миграция Keychain, privacy, подписанные устройства и утверждённые релизные gate) сохраняются и не отменяются этой таблицей.
