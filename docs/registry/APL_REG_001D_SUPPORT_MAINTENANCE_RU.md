# APL-REG-001D — сопровождение и техническое обслуживание

Версия регистрационного экземпляра: **0.2.9**

## 1. Модель сопровождения

Arvectum Proxy Launcher сопровождается как версионируемый desktop-продукт. Изменения проходят через исходный репозиторий, автоматические тесты, release policy и публикацию immutable release assets с SHA-256 manifest.

Базовые операции сопровождения:

- регистрация дефекта и воспроизводимого сценария;
- исправление в исходном коде;
- автоматизированные source/unit/integration проверки;
- платформенные acceptance-gates для изменений, затрагивающих системный proxy/lifecycle;
- сборка релизных пакетов;
- публикация release notes и `SHA256SUMS.txt`;
- зеркалирование релиза в российский контур в соответствии с release/lifecycle policy.

## 2. Обновления

Обновление выполняется установкой нового версионированного пакета. Перед обновлением активная proxy-сессия должна быть завершена штатно либо восстановлена. Новая версия не должна уничтожать незавершённый rollback evidence предыдущей версии без отдельной доказуемой миграции.

## 3. Обработка сбоев

При проблеме, затрагивающей сетевую конфигурацию:

1. прекратить новые destructive изменения;
2. сохранить диагностику без секретов;
3. проверить durable recovery evidence;
4. выполнить штатный recovery;
5. если обнаружено стороннее значение — не перезаписывать его автоматически;
6. только после восстановления удалять/обновлять пакет.

## 4. Каналы поддержки

Публичный технический канал проекта — issue tracker репозитория `arvectum2/proxy-launcher`. Официальные e-mail/телефон поддержки для заявления должны быть утверждены правообладателем и внесены в закрытый filing bundle (`PRIVATE/HUMAN`); этот публичный документ не подменяет корпоративные контактные сведения.

## 5. Жизненный цикл и российский контур

Требования к owner-operated source/build/storage/distribution perimeter описаны в `APL-REG-001B_SOVEREIGN_LIFECYCLE.md`. Репозиторная автоматизация сама по себе не доказывает физическое размещение или российский контроль инфраструктуры. До подачи должны быть приложены фактические evidence: местонахождение/оператор, доступы, build host, хранилище исходников, выпуск и распространение — без публикации секретов.

GitHub допускается как публичный/вторичный канал исходников и release bytes; российское зеркало GitVerse существует как независимый канал распространения. Если критерий заявки требует конкретного российского authoritative perimeter, заявлять его можно только после физического подтверждения APL-REG-001B.

## 6. Сроки реакции

Публичный open-source repository не устанавливает договорный SLA. Любой коммерческий SLA, график поддержки или гарантийные обязательства должны соответствовать реальному договору ООО «Арвектум» и вводятся в заявление/приложения только после `HUMAN` утверждения.
