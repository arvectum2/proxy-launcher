# APL-REG-001D — процедура экспертной проверки

Цель: дать эксперту короткий воспроизводимый путь для подтверждения, что переданный экземпляр `Arvectum Proxy Launcher 0.2.9` соответствует заявленным функциональным характеристикам.

## 1. Подготовка

Получить релиз `v0.2.9` и `SHA256SUMS.txt`. Проверить SHA-256 каждого тестируемого пакета. Зафиксировать:

- имя файла;
- SHA-256;
- ОС/версию/архитектуру;
- дату проверки;
- результат каждого шага PASS/FAIL.

Тестовый upstream proxy должен быть законным и специально предоставленным для проверки. Секреты proxy не включаются в публичный протокол.

## 2. Windows x64

1. Установить Setup для текущего пользователя либо распаковать portable.
2. Запустить программу без отключения Defender/SmartScreen/firewall.
3. Указать тестовый upstream proxy и bypass/no_proxy.
4. Включить приложение; проверить управляемый system proxy/PAC и локальный endpoint.
5. Проверить сетевой запрос через целевое приложение.
6. Штатно отключить; убедиться, что baseline восстановлен.
7. Повторить с аварийным завершением/перезапуском и проверить recovery.
8. Во время активной сессии изменить одно управляемое системное значение на третье, не равное original и Arvectum; recovery не должен молча перезаписать его.
9. Закрыть тестовую сессию и удалить Setup-редакцию штатно.

## 3. Astra Linux 1.8 x86-64 / Fly

Установка:

```bash
sudo apt install ./Arvectum-Proxy-Launcher-0.2.9-astra-linux-amd64.deb
arvectum-proxy-launcher
```

Проверить:

1. приложение запускается;
2. NetworkManager получает ожидаемую proxy/PAC конфигурацию;
3. desktop GSettings получает ожидаемую конфигурацию для сценария Firefox «использовать системные настройки прокси»;
4. `no_proxy`/bypass не отправляет localhost через внешний proxy;
5. штатное отключение восстанавливает baseline;
6. crash/reboot recovery восстанавливает доказуемое Arvectum/original состояние;
7. третье внешнее значение вызывает fail-closed вместо перезаписи;
8. после финального отключения не остаётся активного recovery-autostart/evidence, которое должно было быть закрыто.

## 4. RED ОС 8.0.3 x86-64 / KDE

Установка:

```bash
sudo dnf install ./Arvectum-Proxy-Launcher-0.2.9-redos-linux-x86_64.rpm
arvectum-proxy-launcher
```

Проверить:

1. platform label — `Linux / RED OS`;
2. package integrity/system package verification не показывает непредусмотренной модификации файлов;
3. enable/disable proxy lifecycle;
4. Chromium/system-PAC сценарий;
5. localhost/no-proxy bypass;
6. crash recovery;
7. reboot recovery;
8. mixed-state, состоящий только из original/Arvectum значений, восстанавливается безопасно;
9. действительно третье/чужое значение блокирует destructive rollback;
10. emergency rollback/cleanup и удаление/повторная установка проходят штатно.

## 5. Критерий совместимости с двумя ОС

Для filing evidence приложить два отдельных протокола физической проверки точных передаваемых бинарных пакетов, по одному для Astra Linux и RED ОС, с версиями ОС, архитектурой, SHA-256 и подписью/атрибуцией ответственного проверяющего.

Существующие проектные записи доказывают физическое Linux-поведение линии 0.2.8 и совместимость целевых Astra/RED систем. Поскольку `v0.2.9` декларирует неизменное Linux-поведение, но является новым release set, **предпочтительный pre-submit gate — повторить этот сокращённый smoke для exact public 0.2.9 DEB/RPM**.

Статус доверенности самих ОС для целей постановления №1236 определяется по актуальным государственным реестровым сведениям на дату подачи и не выводится только из успешного технического теста.

## 6. Успешный итог

Экспертный протокол считается технически закрытым, когда для каждого заявленного обязательного runtime:

- hash совпадает с переданным экземпляром;
- установка/запуск успешны;
- основная proxy-функция подтверждена;
- штатный rollback подтверждён;
- recovery подтверждён;
- foreign-state protection подтверждена;
- удаление/cleanup не оставляет управляемую конфигурацию в повреждённом состоянии.
